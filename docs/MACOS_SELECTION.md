# Перевод выделения на macOS

Как довести перевод выделенного текста на macOS до состояния, пригодного для нетехнических
пользователей. Документ описывает, что уже работает, что упирается в системное разрешение и что
действительно требует новой реализации.

## Разрешение обойти нельзя

Три вещи, на которых держится функция, на macOS закрыты одним разрешением — **Универсальный
доступ** (Privacy & Security → Accessibility):

| Что делает приложение | Механизм | Без разрешения |
|---|---|---|
| Ловит одиночный Shift | JNativeHook, перехват клавиатуры | события не приходят, молча |
| Читает выделение | `Robot` шлёт Cmd+C в чужое окно | нажатие не доставляется |
| Читает чужой интерфейс | Accessibility API | доступ запрещён |

Программно выдать это разрешение невозможно — Apple намеренно требует ручного действия
пользователя, иначе любая программа могла бы читать всё, что он печатает. **DeepL требует того же
самого**: их приложение не обходит разрешение, а аккуратно его запрашивает. Значит, задача — не
избавиться от шага, а свести его к двум кликам.

## Что уже работает, а что нет

Важное наблюдение: код после чтения текста **не привязан к Windows**. Классификация выделения
умеет работать по содержимому буфера обмена (`classifyPortableSelectionSurface` в
`SelectionSurfacePolicy.kt`), и от неё же зависит выбор между всплывающей кнопкой и автоматическим
переводом.

Обрыв происходит раньше — в `MainGlobalKeyListener.kt`: если скопировать выделение не удалось,
обработчик выходит до всякой классификации. Отсюда наблюдаемое «нет ни перевода, ни кнопки».

Ожидаемое поведение после выдачи разрешения:

| Что выделено | Буфер обмена | Результат |
|---|---|---|
| Текст на странице в браузере | есть HTML-разметка | `READ_ONLY` → автоматический перевод |
| Поле ввода, редактируемая область | признак редактируемости | `EDITABLE` → кнопка перевода |
| Только простой текст | ничего кроме текста | `UNKNOWN` → кнопка перевода |

То есть автоперевод на macOS должен заработать без новой реализации детектора — в упрощённом
виде, по эвристике буфера обмена вместо точных признаков Accessibility API.

**Это предположение, а не проверенный факт.** Подтверждается или опровергается этапом 0.

## План

### Этап 0. Проверка гипотезы (ничего не программируем)

Выдать разрешение вручную на тестовом Mac и проверить: срабатывает ли Shift, читается ли
выделение, появляется ли автоперевод на странице в браузере.

Результат определяет объём остальной работы. Если автоперевод заработал — этап 3 из
обязательного превращается в улучшение качества.

Диагностика при неудаче — журнал пишет строку `Selection presentation: surface=…, presentation=…`
с полным разбором признаков.

### Этап 1. Запрос разрешения внутри приложения

Ради этого этапа всё и затевается: модель не должна искать настройку сама.

1. **Проверка состояния.** `AXIsProcessTrusted()` из ApplicationServices — простая функция без
   параметров, привязывается через JNA, который в проекте уже используется.
2. **Системный запрос при первом запуске.** `AXIsProcessTrustedWithOptions` с
   `kAXTrustedCheckOptionPrompt` показывает штатное окно macOS с кнопкой «Открыть настройки».
   Требует работы с CFDictionary, что из JNA неудобно, — проще вызвать из уже существующего
   загрузчика `packaging/macos/CamWorkBootstrap.c`, который и так собирается clang в CI.
3. **Экран объяснения в приложении** на случай, когда разрешения нет: короткий текст, зачем оно,
   и кнопка, открывающая нужную страницу напрямую:
   `x-apple.systempreferences:com.apple.preference.security?Privacy_Accessibility`
4. **Повторная проверка** раз в несколько секунд, пока окно открыто, и сообщение об успехе, —
   чтобы пользователю не пришлось гадать, подействовало ли.
5. **Внятная ошибка вместо нынешней.** Сейчас при отсутствии разрешения показывается
   `capture_failed` — «Не удалось прочитать выделенный текст», что не подсказывает ничего.

Объём небольшой, эффект наибольший.

### Этап 2. Developer ID и нотаризация

Без этого этап 1 бессмыслен для реальной раздачи. macOS привязывает выданное разрешение к
подписи приложения: у ad-hoc подписи она меняется с каждой сборкой, поэтому **после каждого
обновления разрешение придётся выдавать заново**, удаляя старую запись из списка. Для
нетехнического пользователя это неприемлемо.

Плюс без нотаризации Gatekeeper требует ручного снятия карантина при первой установке.

Требует Apple Developer Program — 99 $/год. Инфраструктура в CI уже написана и включается
секретами репозитория.

### Этап 3. Родной детектор выделения для macOS

Даёт паритет с Windows и убирает костыли. Делать после этапов 0–2, объём сопоставим с
существующим `WindowsSelectionSurfaceDetector`.

Что даёт:

- **Чтение выделения без буфера обмена.** `AXUIElementCreateSystemWide()` →
  `kAXFocusedUIElementAttribute` → `kAXSelectedTextAttribute` возвращает выделенный текст
  напрямую. Исчезает подмена пользовательского буфера обмена и синтетический Cmd+C со всеми его
  побочными эффектами.
- **Точная классификация.** Признак редактируемости берётся из роли элемента
  (`kAXRoleAttribute`, `AXTextField`/`AXTextArea`) и `kAXSettableAttribute`, а не угадывается по
  разметке в буфере.
- **Правильное положение кнопки.** `kAXSelectedTextRangeAttribute` вместе с
  `kAXBoundsForRangeParameterizedAttribute` дают экранные координаты самого выделения, а не
  позицию курсора.

Как вызывать из Kotlin — два варианта:

| Подход | За | Против |
|---|---|---|
| JNA к ApplicationServices | без новых артефактов сборки | ручная возня с типами CoreFoundation, легко ошибиться с владением памятью |
| Отдельный native-помощник (Swift/ObjC), запускаемый процессом | нормальные типы, тестируется отдельно | ещё один бинарник в бандле и в подписи |

Рекомендация — **помощник**: инфраструктура сборки нативного кода в macOS-скрипте уже есть, а
ручное управление памятью CoreFoundation через JNA — известный источник трудноуловимых сбоев.

Отдельная деталь: Chromium на macOS раскрывает дерево Accessibility не всегда. Может
потребоваться выставить элементу приложения атрибут `AXManualAccessibility` — это тот же класс
проблем, что описан для Chromium в истории версий 1.1.7 на Windows, и его стоит заложить в оценку.

## Порядок

Этап 0 → этап 1 → этап 2 → (по результатам) этап 3. Этапы 1 и 2 независимы и могут идти
параллельно: второй упирается во внешнюю покупку, первый — чисто наша работа.
